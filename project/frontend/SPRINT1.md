Sprint 1 Report: Interview Reflections Frontend 

## Project Recap: 
This is a single-user browser dashboard for a college student preparing for software engineering/computer science technical interviews. A user enters a reflection on a coding problem, saves it, sends it to AI, and then can view a structured learning summary (key concept, knowledge gap, takeaway, area for review). Sprint 1 builds exclusively the front-end of this workflow, as the AI and data stored are currently simulated. 

**NOTE: Initial state loads from mock_data.json, per the course slides. The page also carries its live state in `data-*` attributes. Adds, edits and deletes live in memory only, thus the website updates upon changes, but refreshing the page reverts everything back to the contents within mock_data.json. 

## Workflow Demo Guide:
1. In a terminal, run python3 -m http.server from the project/frontend folder. Open http://localhost:8000 in Chrome, Firefox, or Edge. 
2. The page shows 5 entries from mock_data.json. The statistics read 5 total entries, a 60% solve rate, and 29 minutes average time. 
3. Each card has a colored result and difficulty badge. Two cards already show an AI review, the other three show "No AI review yet." The card reading "Longest increasing Subsequence" had no approach text, thus the "Send to AI" button is disabled. 
4. Click "Add entry" on an empty form. Every required field shows its own error. Numbers such as 0, 601, or 2.5 being entered into the time section results in an error. Start typing in a field and its error clears. 
5. Fill all required fields and click "Add entry." A new card appears at the bottom of the list without reloading the page. The stats update, and the form resets. 
6. Click "Send to AI" on "Binary Search" or the card you created. The button disables and reads "Analyzing..." for roughly 1.5 seconds, then the card shows the four-field summary. The button reads "Re-run review" Typically, it will give another AI-generated response, but at this stage in the project, it will repeat the same base text. 
7. Click "Edit" on any card. The form fills with that entry, the submit button reads "Save changes," and a "Cancel" button appears. Change the result and save, as the card will update in place and the stats recalculate need be. In a second edit, click "Cancel" instead and notice nothing changes. 
8. Click "Delete" and cancel the confirmation: the card remains. Click "Delete" and confirm this time: the card is removed, and the stats update as necessary. Delete every entry and the stats update to "--" and an empty-list message in place of the cards. 
9. Narrow the window below 768px. The layout becomes one column with the form first. If you click edit on a card, you are directed to the form section to edit the card. At 768px and wider, the form and the entry list sit side by side and scroll independently. 
10. Reload the page and watch all changes disappear, with the original five entries reappearing. 

## AI Usage Log & Reflection 
After writing the SPEC.md file in project, I attached it as the context for GitHub Copilot to aid in constructing the app.js, index.html, mock_data.json, and style.css files as needed. I started with the mock data, asking Copilot the following: "#SPEC.md, Section 2 (the mock_data.json rules), create project/frontend/mock_data.json. Follow the field names, entry counts, and ai_review shape exactly. Create only this file." Copilot added the file seamlessly, accepting the code as generated. I provided other prompts constructing of the HTML and CSS files in the context of the SPEC. Lastly, the JS file took several prompts, as I had separated them into loading and rendering, form creation, editing and deleting, and mock AI were each constructing in several prompts largely from Section 3 of the SPEC. Most of the website was generated smoothly, yet AI ran into a few errors. After adding independent scroll bars for the form section and card section, the form section scroll bar caused the boxes to type in get crammed together, which was visually unappealing. I asked AI to shift that scroll bar slightly to the right, with the prompt "Shift the scroll bar over to the right slightly. Start with a few pixels. Adjust the style.css and index.html as necessary." After failing to do so, I provided a new prompt: "Can you shift only the left scroll bar, the one used for the form section, 1.0 rem to the right? Keep the other scroll bars as is." This one worked well. Additionally, the validation used every(), which stops at the first invalid field. As a result, one error in the form section would show at a time, rather than every error needed to be fixed. On secondary buttons the :active state set the label and background to the same dark green. As a result, the text vanished when the button waspressed, and the focus ring was too pale to see. These were quite easy to call Copilot out on, and simply fix by providing the agent with a straightforward prompt addressing the issue and what to fix and change specifically. The SPEC had also contradicted itself at one moment, particularly on entry ids (max + 1 versus never reused). I removed the never-reused line to match the code. Overall, Copilot followed explicit structural rules well but missed behavior that crosses interactions and rules that must hold across all files, creating issues.
